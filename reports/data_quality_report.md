### Проблема №1

**Расположение:** `Invoice` (столбец A)

**Суть:** 19500 строк помимо шестизначного номера содержат в начале букву.

**Количество:** 19500 (19494 «C» — отменённые заказы, 6 «A» — списание безнадёжного долга), 1.83% от общего числа строк.

**Причина:** «C» — стандартное обозначение отменённого заказа. «A» — списание безнадёжного долга (bad debt), подтверждено текстом `Description` ("Adjust bad debt") для всех 6 строк.

**Решение:** С помощью Python определены отменённые заказы (флаг `IsCancelled`) и списания безнадёжного долга (флаг `IsBadDebt`) как отдельные булевы столбцы — для удобной последующей фильтрации без потери исходной информации. Также создан отдельный столбец `InvoiceNumber` с номером транзакции без буквенного префикса, для использования в группировках, где нужен только числовой идентификатор заказа.

### Проблема №2

**Расположение:** `StockCode` (Столбец B) 

**Суть:** 134986 строк (12.65%) содержат буквенные значения в `StockCode` — но это слишком широкий критерий, включающий и совершенно нормальные коды вида «85123A» (5 цифр + буква-суффикс, стандартный формат товара). При проверке по более точному критерию — соответствию формату «5 цифр + опционально одна буква» — обнаружено 7466 строк (0.70%), реально не являющихся товарными кодами (`POST`, `DOT`, `M`, `BANK CHARGES`, gift-коды и др.).

**Количество:** 134986, 12.65 % от общего числа строк; 7466, 0.7 % от общего числа строк

**Причина:** Исходя из текста `Description` можно определить чем является каждый нестандартный код: тестовой транзакцией, подарочный купоном или отмененным заказом. 

**Решение:** С помощью регулярного выражения (`^\d{5}[A-Za-z]?$`) определён стандартный формат товарного кода (5 цифр, опционально с одной буквой на конце). Все строки, не соответствующие этому формату, помечены булевым флагом `IsServiceCode` — не удалены физически, чтобы сохранить данные для финансового анализа. 

### Проблема №3

**Расположение:** `Description` (Столбец C) 

**Суть:** 4382 строки (0.41%) не содержат описания товара.

**Количество:**  4382, 0.41 % от общего числа строк, из них 363 строки относятся к 355 уникальным `StockCode`, у которых нет описания 
ни в одной строке, что делает их невосстановимыми

**Причина:** Для большей части строк (4019) описание отсутствует только в конкретной транзакции, но присутствует у того же товара (`StockCode`) в других строках — вероятно, техническая недоработка. Для оставшихся 363 строк (355 уникальных `StockCode`) описание отсутствует полностью и системно — все эти строки также имеют `Price` = 0 и `Quantity` < 0, что указывает на отдельную категорию операций (списание/корректировка складских остатков), не относящуюся к обычным продажам.

**Решение:** Восстановить строки, если есть такая возможность. Где таковая возможность отсутствует, сделать маркировку булевым флагом `IsStockAdjustment` для фильтрации. 

### Проблема №4

**Расположение:** `Quantity` (Столбец D) 

**Суть:** Всего 22950 (2.15 %) строк имеют отрицательное `Quantity`; 19493 (84.9 %) из них являются отменными заказами, 303 (1.32 %) является списаниями, оставшиеся 3154 строки необъяснимы

**Количество:** 22950, 2.15 % от общего числа строк; 19493 (84.9 %) из них являются отменными заказами (`Quantity < 0`, `Invoice` начинается с `C`), 303 (1.32 %) из них являются списаниями (`Quantity` < 0, `Price` = 0), остальные 3154 (13.7 %) строки необъяснимы

**Причина:** Большинство отмен объяснимо отменами заказов, а также списаниями товаров в магазине. Оставшаяся часть не поддаётся объяснению без дополнительных данных. 

**Решение:** Для данной проблемы нету единого решения. Растановка флагов при решении предыдущих и последующих проблем автоматически решит часть данной проблемы. В то же время, оставшиеся строки составляют малую часть базы данных (0.32 %) и слишком разнородны, из-за чего они и не обозначены флагом и их можно проигнорировать при анализе датасета. При необходимости, эти строчки можно выделить с помощью условия: `Quantity < 0 AND IsCancelled = 0 AND IsStockAdjustment = 0`

### Проблема №5

**Расположение:** `Customer` (Столбец G)

**Суть:** 243007 строк не имею `Customer ID` (5-значное цифровое значение)

**Количество:** 243,007 строк (22.77 %) на всю базу данных; 

**Причина:** Скорее всего, эти строки представляют собой гостевые покупки без регистрации — пропуски консистентны на уровне целого Invoice (либо весь заказ имеет `Customer ID`, либо не имеет вовсе; частичных пропусков внутри одного заказа не обнаружено). Гипотеза дополнительно подтверждается тем, что для двух стран (`Bermuda`, `Hong Kong`) `Customer ID` отсутствует у 100% заказов.

**Решение:** возможности восстановить ID (как в случае с `Description`) нету. Из-за большого количества подобных строк их нельзя исключить из анализа (как в случае со строками, где `Quantity` < 0). Их следует пометить флагом `IsGuest` для последующего анализа.

### Проблема №6

**Расположение:** `Country` (Столбец H) 

**Суть**: 21139 строчек не имеют единого форматирования в датасете: некоторые используют абревиатуры для обозначения страны (`EIRE`, `USA`, `RSA`), регион (`West Indies`), острова (`Channel Islands`, `Bermuda`) или сообщества (`European Community`), вместо страны, или не имеют конкретной страны (`Unspecified`). 

**Количество:** 21139 строк (1.98 %) на всю базу данных

**Причина:** Непостоянность в записях можно обозначить простыми ошибками при записи. Важно отметить, `European Community` — вероятно, нестандартное обозначение страны для одного конкретного клиента (Customer ID 15108), а не пробел в данных; отнесено к общей категории нестандартной географии по той же причине незначительного объёма, но природа отличается от Unspecified/островов.

**Решение:** Создание колонки `country_clean`, для единого формата названий стран. Островные государтства, регионы, сообщества и неопределенные территории нужно пометить флагом `IsNotStandardGeography`.
